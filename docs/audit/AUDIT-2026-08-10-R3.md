## 第二部分：本轮新发现

### 发现 1（High）— owner 用 `setSalesPaused` 独占整包奖池

#### 问题

FR-C-24 声称「不存在任何形式的管理员函数能动到未领奖金」，首轮自查也确认
「owner 直接搬奖池：确无 `sweep`/`emergencyWithdraw`，资金出口只有中奖者与 treasury」。

**这两句话都是对的——但 owner 根本不需要「搬」。他可以合法地把奖池「赢」走。**

`setSalesPaused` 是 FR-C-22 明确授予 owner 的三项权限之一，它只影响 `buyTickets`
（FR-C-23 如此要求，实现也确实如此）。问题在于，「只影响 buyTickets」正是
**「决定谁能参与本期」**的开关：

1. 等某期开出且奖池已经很肥（缓冲区刚释放 / 第三方 `injectPot` / 大额滚存）
2. 立刻 `setSalesPaused(true)`——**整个售票窗口内没有任何人能买票**
3. 在 `closeTime - 1` 秒，同一笔交易里 `setSalesPaused(false)` + `buyTickets(8)`
   （owner 用一个合约把两步打包即可，8 张恰好覆盖默认配置的全部 8 个中奖 slot）
4. 成为唯一买家 → 持有全部票号 → 必中全部奖级 → `claim` 领走整包奖池

全程没有任何「异常」调用：暂停、恢复、购票、开奖、领奖，每一步都是合约设计内的
正常操作，链上看不出任何越权痕迹。

#### 为什么这和已修复的那个 Critical 是同一类

首轮的 Critical 是「owner 换 VRF 随机源 → 离线挑种子 → 稳中头奖 → 合法领走」。
本条是「owner 关闭售票 → 强制自己成为唯一买家 → 必中全奖级 → 合法领走」。

**两者都不是偷，都是通过操纵一个被授予的权限，把「概率性的中奖」变成「确定性的获取」。**
首轮修复堵住了「操纵随机数」这一条，但「操纵参与者集合」这一条一直敞着——
而且后者更简单，不需要部署假合约，不需要暴力搜种子。

#### PoC 实测

`AuditPoC2Test.test_PoC_OwnerPauseSqueezeCapturesEntirePot`：

```
owner spent (USDC): 8.000000
owner won   (USDC): 106.920000
net profit  (USDC): 98.920000
```

测试中还断言了诚实用户 bob 在暂停期间买票被 `SalesArePaused` 拒绝——
他从头到尾没有任何机会参与这一期。

#### 影响

- 直接推翻 FR-C-24 的安全声明与首轮自查「owner 无法挪用奖池」的结论
- 可吃掉的金额 = 该期 pot，包含**所有第三方注资、所有滚存进来的过期奖金、
  所有未开出奖级的 carry**——正是运营方与其他玩家累积起来的钱
- 无需 keeper 缺席、无需 VRF 异常、无需内存池可见性，**任何时候都可执行**

### 发现 2（Medium）— 修复 A 的残余：攻击者仍能决定接收缓冲区那一期的窗口长度

#### 问题

修复 A 的安全论据是：carry 只交给 `_openNextRound` 开出的新期，
而**「新期拥有完整、未封盘的售票窗口，无人能预先卡位」**。

前半句成立，后半句不成立。新期的 `closeTime` 取的是「晚于 `block.timestamp`
的最近一个场次」：

```solidity
do {
    t += s_intervals[cursor];
    cursor = (cursor + 1) % len;
} while (t <= block.timestamp);
```

而 `performUpkeep` **无权限、任何人可调**——所以调用时刻由调用者选，
新期的售票窗口长度也就由调用者选。攻击者卡在下一个场次前 1 秒调用
`performUpkeep`，新期就只有 **1 秒**售票窗口，而缓冲区恰好在这一刻并入它的 pot。
同一笔交易里接着 `buyTickets` 即可独占。

#### 前提与其成立性

需要 keeper 缺席（否则 keeper 会在 `drawTime` 就推进，窗口是完整的）。
这看似是很强的前提，但：

- **SPEC Q8 明确写了「keeper 本就不在信任边界内」**，安全性不得依赖它按时执行。
  这正是 `performUpkeep` 设计成无权限的理由——那么它被恶意择时也必须是安全的
- 需要的缺席时长 ≈ 一个间隔（默认 2 天）。而 `Deploy.s.sol` 的
  `FAST_INTERVAL_SECONDS` 分支（文档里用于「数小时内跑通真实 VRF 全链路」）
  是单一间隔部署，间隔 7200 秒时只需 keeper 缺席 **45 分钟**
- 缓冲区里的钱恰恰是在低参与度、长期无人问津时累积起来的——
  与 keeper 失灵的场景高度相关

#### PoC 实测

`AuditPoC2ScheduleTest.test_PoC_AttackerChoosesSalesWindowLengthOfCarryRound`
（单一间隔部署，使场次网格可预测）：

```
attacker spent (USDC): 8.000000
attacker won   (USDC): 106.920000
```

测试中断言了 `window == 1`（1 秒售票窗口），并断言其他人随后买票被
`SalesClosed` 拒绝。

这条同时**吞并了第二轮报告的发现 H**（构造器只要求 `interval > SEAL_GAP`，
可配出售票窗口近乎为零的期）——H 当时定为 Low 是因为它需要错误配置，
现在看它是可以在运行时被攻击者触发的。

## 第三部分：修复建议（按杠杆排序）

### 建议 1（必做，一招同时解决发现 1、发现 2 与首轮 #2）—— 最低参与度门槛

**滚存与注资进来的钱，只有在本期参与度达标时才可分配；否则重新入缓冲区。**

这正是首轮自查列的候选 (a)，当时标记「待决策」。本轮结论：它不是可选的经济调优，
而是两条攻击路径的**承重墙**。

```solidity
uint32 public constant MIN_TICKETS_FOR_CARRY = 32; // 或 ≥ 4 × 总 slot 数

// fulfillRandomWords 里，切分奖池前：
uint256 pot = r.pot;
uint256 carryIn = r.tier1Carry;
if (r.ticketCount < MIN_TICKETS_FOR_CARRY) {
    // 参与度不足：本期只分配本期自己卖票所得，外来的钱原样退回缓冲区
    s_pendingTier1 += carryIn;
    carryIn = 0;
    // 若要更严格，可把「注资额」也单独记账并一并退回
    emit PrizeRolledOver(roundId, s_currentRound + 1, /* 退回额 */ 0);
}
```

效果：攻击者（包括 owner）即便成为唯一买家，也**只能赢回自己那 8 张票对应的奖池
（扣掉手续费后是净亏损）**，拿不到任何滚存/注资的钱。发现 1 与发现 2 的收益
从 +98.92 USDC 变成 −0.08 USDC，攻击彻底失去经济动机。

注意门槛要用**票数**还是**独立买家数**需要权衡：票数门槛可被攻击者用
32 USDC 买满绕过（但那时他要付 32 USDC 才能拿一个不确定收益，
且他仍需独占——可结合建议 3）；独立地址数门槛可被女巫绕过。
建议用票数门槛 + 建议 3 的组合，而不是单点防御。

### 建议 2（必做，解决发现 2 与旧 H）—— 最小售票窗口

`_openNextRound` 跳过距今太近的场次：

```solidity
uint64 public constant MIN_SALES_WINDOW = 6 hours; // 需 < 最小 interval - SEAL_GAP

do {
    t += s_intervals[cursor];
    cursor = (cursor + 1) % len;
} while (t <= block.timestamp + MIN_SALES_WINDOW);
```

构造器同步把校验收紧为 `intervals[i] > SEAL_GAP + MIN_SALES_WINDOW`。
这样无论谁在什么时刻调 `performUpkeep`，开出的期都至少有 6 小时可供他人参与。

代价：极端延迟时会多跳过一个场次，符合 Q2「跳过已错过的场次」的既有语义。

### 建议 3（必做，解决发现 1）—— 暂停不得在本期窗口内解除

让 `setSalesPaused` 的变更只对**此后新开出的期**生效，当前期的售票状态在开期时锁定：

```solidity
// Round 增加一个字段，在 _openNextRound 里快照
r.salesPausedAtOpen = s_salesPaused;
// buyTickets 检查 r.salesPausedAtOpen 而非全局 s_salesPaused
```

这样 owner 想排除他人就必须在开期前决定，而一旦决定，他自己也买不了这一期。
「暂停」回归它应有的语义（停止发行新的一期售票），失去「清场后自己进场」的能力。

若嫌改动大，退而求其次：`setSalesPaused(false)` 时记录时刻，
`buyTickets` 要求 `block.timestamp >= s_unpausedAt + MIN_SALES_WINDOW` 或
本期 `closeTime` 之前至少还有 `MIN_SALES_WINDOW`——但这是补丁式的，
不如快照干净。

## 结论

第二轮的修复质量是好的：方向正确、实现无误、回归测试有真断言、不变量同步更新。
问题在于**修复的范围是按上一份报告的条目走的，而不是按根因走的**。

发现 1 与发现 2 说明：只要「一期可以被单一方独占」这件事成立，
就总能找到新的杠杆去撬它——第二轮堵了「钱什么时候进场」，
本轮就从「谁能进场」和「窗口多长」两侧各拿走了一次。

**建议 1（最低参与度门槛）是唯一能从根上终结这一类攻击的改动**，
建议 2、3 是配套的入口收紧。三条都做完之后，
才谈得上首轮自查里那句「资金绝对安全」。

运维层面的判断不变，且因发现 1 而加重：owner = 部署者 = treasury =
VRF 订阅所有者 = CRE 接收器 owner = 同一个 EOA（`0xA7b4…743f`）。
在发现 1 修复之前，**这个私钥可以随时合法取走全部奖池**。
