# 原生 ETH 改造后的 10 轮对抗审计（2026-08-11）

## 为什么要重做

前十轮审计（`SELF-AUDIT-2026-08-09.md`、`AUDIT-2026-08-10*.md`）的结论建立在
**ERC20 语义**上。2026-08-11 把计价资产改成链原生币后，有一条根本性质变了：

> ERC20 的 `transfer` 不会把执行权交给接收方。原生币的每一次派奖都是**一次对
> 任意代码的调用**。

这不是"差不多"的改动——它把「派奖」从一个纯记账动作变成了一个可被劫持的控制流
转移点。因此重入相关的旧结论一律作废重验，并新增了 ERC20 时代根本不存在的攻击面
（强制打款、收款方拒收、收款方耗尽 gas）。

同时，单位从 `1e6` 变成 `1e18`——**六个数量级的跳变**，任何写死的金额都会静默错位。
本轮最严重的发现正是出在这里，且是我自己在改造时引入的。

## F2（High）：注资默认值差了 6 个数量级

### 问题

```tsx
const [injectAmt, setInjectAmt] = useState("100");   // ← USDC 时代写的
...
const amt = parseTokenAmount(injectAmt);              // decimals 从 6 变成了 18
await write(..., "injectPot", [currentId], amt);      // 一键发交易，无二次确认
```

- USDC 时代：`parseTokenAmount("100")` = `100e6` = 100 USDC ≈ **$100**，合理的默认值
- 原生币之后：`parseTokenAmount("100")` = `100e18` = **100 ETH** ≈ **$300,000**

按钮文案只写"💰 注资奖池"，**用户在钱包弹窗之前看不到任何金额**。唯一的防线是
用户在 MetaMask 里逐字读金额——而这恰恰是用户最常跳过的一步。

### 为什么它逃过了改造时的检查

改造时我逐个处理了「读链上金额」的路径（余额、奖池、抽成都改对了），却漏了
**用户输入的默认值**——它不是从链上来的，不在我的检查清单里。这类"常量本身
携带单位语义"的地方是单位迁移最容易漏的位置。

### 修复

1. 默认值改为 `"0.001"`（约 10 张票的量级）
2. **把解析后的真实金额显示在按钮上**：`💰 注资奖池（0.001 ETH）`——不让钱包弹窗
   成为用户第一次看见数额的地方
3. 金额为 0 或超过余额时禁用按钮，并给出明确提示

## F1（Medium）：无分页视图 + 单一异常边界 = 整个面板被打掉

### 问题

`ticketsOwned(roundId, account)` 遍历该期全部 Range，**无分页**：

```
实测 600 条 range：305,808 gas（约 500 gas/条）
外推 5 万条：       ~25,000,000 gas  → 超出多数公共 RPC 的 eth_call 上限
```

灌 5 万条 range 的成本：5 万笔单张购买，票款 5 ETH + gas 约 0.035 ETH。**票款会随
中奖回到攻击者手里**（他持有全场），净成本≈票款的 1%（抽成）+ gas ≈ **0.085 ETH**。

真正的放大器在前端：这次读取此前是裸调在 `refresh()` 的**单一 try 块**里，所以
一期被灌票 → 该读取 revert → 整个 `refresh()` 中断 → **倒计时、奖池、领奖提示
全部停止更新**，对所有用户生效，而不只是被灌票的那一期。

### 关键确认：写入路径不受影响

这正是 Range 压缩存储 + 二分查找的设计意图。已用测试固化：

```
test_ManyRangesDoNotInflateClaimGas：600 条 range 时 claim < 250k gas（O(log n)）
```

所以这是**纯视图层 DoS，无资金风险**。

### 修复

- 合约：NatSpec 写明成本模型、失效规模与攻击成本，明确「调用方必须容忍它 revert」
- 前端：单独包住这一次读取，失败时显示"读取超限"/"—"，其余数据照常刷新
- 刻意**不**改函数签名加分页：它是测试台便利函数（正式前端应由 `TicketsBought`
  事件累加），改签名会破坏已部署的 ABI 而收益有限

## F3（Low）：treasury 必须能收原生币——一条新增的运营约束

ERC20 时代 `safeTransfer` 到任何地址都会成功。改用原生币后，若 treasury 是一个
没有 `receive`/`fallback`（或在其中 revert）的合约，`withdrawFees` 会**永久 revert**。

- 链上无法预先验证（只有真转一次才知道），因此只能由 owner 保证
- **可自救**：owner 改回可收款地址即可解冻
- **奖池不受影响**：抽成与奖池自购票起分账（FR-C-20），坏掉的 treasury 不影响任何中奖者领奖

已写入 FR-C-22 并有验收测试 `test_RejectingTreasuryBlocksFeesButNotPrizes`。

## 各轮查了什么（含未发现问题的部分）

### R1 强制打款（selfdestruct）

原生币可以绕过"没有 receive/fallback"被强塞进合约。若代码任何地方依赖
`address(this).balance` 做分账，强制打款就能篡改结果。

**结论：安全。** 合约全程不读自身余额，所有金额来自账面 storage。
`test_ForceFedEtherCannotDistortAccounting` 强塞 5 ETH 后验证奖池、抽成、
一等奖金额分文未变。代价是这笔钱永久沉没（FR-C-24 无救援手段的直接后果，已知并接受）。

### R2 跨函数重入

`claim` 自身有 `nonReentrant` 是已知的；本轮查的是**横向**：派奖把执行权交出去时，
合约正处于 claim 中途，别的入口能否观察或改写这份中间状态。

逐个验证（每个都确认**真的执行到了**，而不是撞别的 revert 造成虚假安全感）：

| 回调里调用 | 结果 |
|---|---|
| `performUpkeep` | 真的执行、期号真的推进；但派奖分文不差，重复领取被 `claimedBits`（CEI，转账前置位）挡住 |
| `withdrawFees` | 被拦——与 claim 共用同一把 ReentrancyGuard |
| `rolloverExpired`（同期） | 被拦——领奖窗口与滚存窗口在时间上严格互斥，无重叠也无空隙 |
| `buyTickets` / `injectPot` | 真的执行，但那是**付了全款**的正常购票，没有白拿 |

> 过程中修正了一个测试缺陷：最初的 performUpkeep 重入测试在当期尚未到开奖时刻时
> 执行，只撞到 `DrawNotDue` 就返回了，**根本没跑到重入路径**。加断言确认
> `didRun == true` 后才算真正验过。

### R3 恶意 treasury

treasury 收抽成时重入，试图二次提取或抢奖池 —— 两条都被同一把 guard 挡住，
奖池完好。

### R4 收款方耗尽 gas

`_sendValue` 转发全部剩余 gas。中奖者在 `receive` 里烧光 gas 只能烧掉自己那笔交易，
不影响其他中奖者（pull 模式，各领各的）。

### R5 领奖窗口边界

`claim` 要求 `t <= settledAt + CLAIM_WINDOW`，`rolloverExpired` 要求 `t > ...`。
逐秒验证：最后一秒可领不可滚存，下一秒可滚存不可领——**无重叠、无空隙**。

### R6 长期停摆后的日程追赶

`_openNextRound` 要逐个跳过错过的场次。快节奏实例（7200 秒）停摆一年 ≈ 4380 次循环，
若 gas 超区块上限则期号永远无法推进 = 全部资金冻结。

**实测通过**：停摆 365 天后 `performUpkeep` 仍远低于 10M gas，且新期拿到完整售票窗口。

### R7 规模

见 F1。补充确认 `winnersOf` / `pendingPrizes` 都被 16 个 slot 硬上界约束，不受灌票影响。

### R8 阶跃函数哨兵

`_openNextRound` 里还剩一处阶跃：

```solidity
if (releasePot == 0 && s_pendingPot > 0 && pctBps >= 5000) releasePot = s_pendingPot;
```

阶跃门槛是前十轮里**被打穿五次**的模式（阈值一跨就能一次性独占整包）。这里之所以
安全，**仅仅因为**：`pctBps >= 5000` 时按比例取整为 0 意味着 `s_pendingPot < 2`，
即只可能在缓冲区余额为 **1 wei** 时触发。

已用 fuzz 把这个前提钉成哨兵（`testFuzz_DustEscapeHatchCanOnlyReleaseOneWei`）：
若将来有人调低 5000 这个阈值，可一次性释放的量会立刻超标而报警。

### R9 金额量级

逐个复核改造后的乘法上界（票款、抽成、奖级切分、缓冲释放、配比预算），
最大约 `1.2e30`，距 `uint256` 上限 `1.16e77` 有 47 个数量级余量。无溢出风险。

反向确认：`buyTickets` 的数量校验排在 `msg.value` 校验**之前**，任何 revert 都会
原路退回 ETH，不存在收了钱不记账的路径。

### R10 经济学复核

「买光全场」在新价格下的收益结构与 USDC 时代**完全一致**（全部按比例计算，
与单位无关）：花 X 买光全场，可捕获至多 X 的 carry，净成本为抽成 1%。

这是抽签制彩票的**固有性质**——攻击者的本金随中奖回到自己手里，任何"滚存"机制
都无法消除。SPEC 已如实记录为不可修复项，`CARRY_MATCH_MULTIPLIER` 只抬高资本门槛
并给其他参与者稀释的机会。**本轮未发现新的经济攻击面。**

## 一个我认为值得单独说的观察

前十轮的元教训是「**每次修复都引入新漏洞，五次，全部经由阶跃门槛**」。

这一轮的元教训不同，是「**跨越语义边界的改造，风险不在被改动的代码里，而在
没被改动却依赖旧语义的代码里**」：

- 合约侧我改得很仔细，10 轮下来没查出资金安全问题
- 真正的 High 出在一个我**根本没动过**的前端常量上——它在旧语义下完全正确，
  在新语义下差了 6 个数量级

`ticketsOwned` 的放大效应也是同一类：函数本身没变，变的是它周围的异常边界假设。

对后续改造的建议：单位/资产语义变更时，检查清单不能只覆盖"我改了哪些地方"，
必须覆盖"**哪些地方的正确性依赖了旧语义**"——尤其是默认值、占位符、阈值常量
这些不从链上读、因而不会在改造中被自然触及的位置。
