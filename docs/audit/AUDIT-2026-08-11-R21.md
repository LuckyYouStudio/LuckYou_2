## K-1（High）— keeper 正在用 owner 私钥无人值守运行，且设计是失败开放的

### 机制

`keeper/keeper.ps1:76-84`：

```powershell
$pk = $envMap['KEEPER_PRIVATE_KEY']
if ([string]::IsNullOrWhiteSpace($pk)) {
    $pk = $envMap['PRIVATE_KEY']
    Write-Log 'WARN  未设置 KEEPER_PRIVATE_KEY，正在使用部署者私钥。…'
}
```

配置缺失时脚本**继续执行**，只留一行日志。而 `PRIVATE_KEY` 就是部署账户——
`VRFConsumerBaseV2Plus` 经 `ConfirmedOwner(msg.sender)` 把部署者定为 owner，
所以这把钥匙同时是 `setTreasury` / `setFeeBps` / `setSalesPaused` /
`transferOwnership` / **`setCoordinator`** 的钥匙。

密钥随后进入进程命令行（`keeper.ps1:106-109`、`149-152`）：

```powershell
'send', $lottery, 'performUpkeep(bytes)', '0x', '--private-key', $pk, '--rpc-url', $rpc
```

Windows 上任何同用户（或更高权限）进程都能从 `Win32_Process.CommandLine` 读到它；
若开了进程创建审计（事件 4688 含命令行）或装了 Sysmon/EDR，它还会被**持久化进日志并常被外送**。

### 这不是假设——是当前实际状态

本机 `keeper/keeper.log` 自 19:57 起每分钟一条，无一例外：

```
2026-08-11 20:16:57  WARN  未设置 KEEPER_PRIVATE_KEY，正在使用部署者私钥。…
```

计划任务确实在跑（`Get-ScheduledTaskInfo`：`LastTaskResult = 0`，
`NumberOfMissedRuns = 0`，`Execute = wscript.exe`，`UserId = liush`，`LogonType = Interactive`）。

### 后果

keeper 本身不需要任何特权（`performUpkeep` / `retryDraw` 都是无权限函数），
所以泄露的**不是 keeper 的能力，而是 owner 的能力**。而 owner 能力里最危险的一条
正是 R20 M-2：攻击者调一次 `setCoordinator(任意地址)`，此后所有 VRF 回调恒
`CoordinatorTampered`，`i_coordinator` 是 immutable 无法重新钉死，FR-C-24 禁止任何救援
⇒ **全部奖池永久冻结，且不可恢复**。这是整个威胁模型里最坏的结局，而它现在挂在
一台桌面机的 `.env` 明文文件上。

### 利用前提与成本

- 前提：在这台机器上取得**任意**代码执行（同用户即可，不需要提权），或能读取
  进程命令行 / 4688 日志。配合 K-2，「任何本机已认证用户」就够了。
- 成本：一次 `setCoordinator` 调用的 gas。攻击者拿不走一分钱，但能让所有人永远拿不到钱。

### 修复方向（不擅自实现）

1. **改成失败关闭**：找不到 `KEEPER_PRIVATE_KEY` 就 `Write-Log ERROR` 并 `exit 0`，
   **绝不回退到 `PRIVATE_KEY`**。一个 keeper 停摆只是开奖延迟（README 自己说的），
   代价远小于把 owner 钥匙交给它。
2. **`keeper/README.md:67-68` 的那句话是错的**，需要一并订正：

   > 原因：`cast` 只接受 `--private-key`，密钥会出现在本机进程命令行里。

   实测 `cast send --help`，本机 foundry 1.7.1 明确支持
   `--keystore`（`[env: ETH_KEYSTORE]`）、`--account`（`[env: ETH_KEYSTORE_ACCOUNT]`）、
   `--password-file`（`[env: ETH_PASSWORD]`）与 `-i/--interactive`。
   即 `cast wallet import keeper --private-key …` 一次，此后
   `cast send … --account keeper --password-file <路径>`，**原始私钥再也不出现在命令行上**。
   接受「命令行暴露」的那条理由不成立，有现成的替代。
3. owner 与 keeper 必须是不同账户；理想情况下 owner 是多签（SPEC FR-C-22 已要求，尚未落实）。

## K-2（Medium）— keeper 脚本对任何本机已认证用户可写

### 证据

```
> icacls C:\test
C:\test  …
         NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)

> icacls C:\test\LuckYou_2\keeper\keeper.ps1
         NT AUTHORITY\Authenticated Users:(I)(M)
> icacls C:\test\LuckYou_2\keeper\run-hidden.vbs
         NT AUTHORITY\Authenticated Users:(I)(M)
```

`(I)` = 继承。根因是 `C:\` 的默认 DACL 带一条
`Authenticated Users:(OI)(CI)(IO)(M)`——**在 `C:\` 下直接建目录，子项就自动对所有已认证用户可写**。

### 后果

计划任务每 60 秒以 `liush`（交互登录）身份执行 `keeper.ps1`。任何本机已认证用户改一行脚本，
最多 60 秒后就以仓库所有者的身份拿到代码执行，随即可读 `contracts/.env` 明文私钥 ⇒ 直接接上 K-1。

任务的 `Execute` 是裸名 `wscript.exe` 且 `WorkingDirectory` 指向同一个可写目录，
理论上还有「同名程序劫持」这条路；但既然脚本本身就可写，这条路径不增加实质暴露面，
**我没有实测它**（需要往用户机器上投放可执行文件，超出审计范围）。

### 利用前提与成本

单用户笔记本上「任何已认证用户」≈ 用户自己，实际风险很低。
但 README 自己写着「正式运营应换成 CRE 或多节点冗余」——**一旦这套脚本被搬到共享机器
或带低权限服务账户的机器上，它就是一条现成的提权链**，而搬迁时没有任何东西会提醒你收 ACL。

### 修复方向

- 把仓库移出 `C:\` 直属目录（放进用户 profile 下），或对 `keeper\` 显式
  `icacls … /inheritance:r /grant:r "%USERNAME%":(OI)(CI)F "SYSTEM":(OI)(CI)F "Administrators":(OI)(CI)F`
- 私钥改用 foundry keystore（DPAPI/口令加密）而非明文 `.env`（与 K-1 的修复方向 2 同一件事）
- 在 `install-task.ps1` 里加一次 ACL 自检，配错就拒绝注册

## K-3（Medium）— `Get-Date -UFormat %s` 在 PS 5.1 返回本地时区纪元

### 机制

`keeper/keeper.ps1:126`：

```powershell
$now = [int64][double]::Parse((Get-Date -UFormat %s))
```

Windows PowerShell 5.1 的 `%s` 是按**本地时间**算的秒数，不是 Unix 纪元。本机实测：

```
UFormat-s: 1786479345.80803
TrueUnix : 1786450545
PSVersion: 5.1.26100.8875
TZ offset : +8 小时      差值 28800 秒 = 恰好一个时区偏移
```

它被用在唯一的判据上（`keeper.ps1:146`）：

```powershell
if (($now - $requestedAt) -lt $timeout) { continue }   # $timeout = 3h = 10800
```

### 后果（**方向取决于运维机器的时区，这才是危险的地方**）

| 机器时区 | `$now` 偏差 | 行为 |
|---|---|---|
| UTC+8（本机） | +28800 | 任何刚进入 DRAWING 的期都被判成「已卡住 8 小时」⇒ 每 10 分钟对**健康**的期发一次 `retryDraw`。合约用 `RetryTooEarly` 挡住（`cast` 估算 gas 时就失败，不上链、不烧 gas），所以**当前只是日志噪音 + 多余 RPC** |
| UTC±0 | 0 | 正确 |
| UTC−5 / UTC−8 | −18000 / −28800 | **兜底被推迟 5 / 8 小时**：合约的 `DRAW_TIMEOUT` 是 3 小时，keeper 却要等到 8 / 11 小时后才肯发 `retryDraw`。R20 M-3 的「已闭环」在这些机器上是**静默失效**的 |

顺带两处同源问题：
- `[double]::Parse(...)` 用当前区域性。本机是 `zh-CN`（小数点为 `.`）所以没事；
  在 `de-DE`/`fr-FR` 上会抛异常 ⇒ 被外层 `catch` 吞成一条 ERROR 日志，**卡住期扫描整段静默停摆**。
- `keeper.ps1:145` 的 `if ($requestedAt -eq 0) { $requestedAt = 0 }` 是空语句（大概想写别的）。

### 修复方向

```powershell
$now = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
```

一行，且顺带解决区域性问题（不再有字符串解析）。

## F-1（Low）— R20 L-2 的修复把领奖扫描变成每分钟 ~72 个 multicall 突发

### 机制

`web/app/page.tsx:278-344`。R20 L-2 指出写死的 `CLAIM_SCAN_ROUNDS = 120` 与注释自相矛盾，
修复改成按链上实测节奏推导，上限 `CLAIM_SCAN_ROUNDS_MAX = 1200`：

```ts
depth = Number(claimWindowSec / avg) + 2;
…
const results = await Promise.all(ids.map(async (id) => { … pendingPrizes … }));
```

对快节奏测试实例（`Deploy.s.sol` 推荐 `FAST_INTERVAL_SECONDS = 7200`）：
`depth = 90 天 / 2 小时 + 2 = 1082`。

`publicClient` 开了 multicall 聚合（`contracts.ts:51-55`）。viem 的分批判据是
`shouldSplitBatch: size > batchSize * 2`，`batchSize` 默认 1024（`viem/_cjs/actions/public/call.js:181,204`），
单位是 hex 字符。`pendingPrizes(uint32,address)` 的 calldata 是 68 字节 = 136 hex 字符，
于是每个 multicall 塞约 `2048 / 136 ≈ 15` 个调用：

**1082 / 15 ≈ 72 个 multicall 请求，一次性并发发出，每 60 秒一轮。**

修复前是 `120 / 15 = 8` 个。也就是说这次修复把该页的周期性 RPC 压力提高了约 **9 倍**，
而这个代价从未被量化。

### 后果

- 本仓库其它地方都有明确的限流纪律（`refresh` 轮询放缓到 10 秒；history 页显式
  `CONCURRENCY = 8` 并注明「超过约 8 路反而更慢」）。`scanClaimable` 是唯一
  **完全没有并发上限**的一处，与自家纪律不一致。
- 整个 `Promise.all` 包在一个 `try/catch` 里：任何一个请求被限流打断，
  **整轮扫描结果全部丢弃**（`catch {}` 什么都不做）。首次加载若撞上限流，
  「你有 N 奖金未领取」的横幅根本不会出现——而这条横幅正是第九轮为
  「别让中奖者错失奖金」专门加的防线。

### 严重度说明

主网官方日程下 `depth ≈ 40`，只有 3 个 multicall，**不受影响**。
受影响的只有快节奏测试实例——恰好就是现在测试网上跑的那种。故记 Low。

### 修复方向

R20 自己给的建议其实更好，只是没被采纳：**从链头倒序扫，遇到第一个
`settledAt + CLAIM_WINDOW` 已过期的期就停**。那样典型情况下只需几次调用，
且不依赖任何常量。若保留当前结构，至少要像 history 页那样加 8 路并发上限 + 分批 `await`。

## T-1 / T-2 / T-3 — 三个假阳性测试，同一个根因

三条都源于同一个误解：**日程是 `[2d, 3d, 2d]` 循环，`s_intervalCursor` 在开期时推进**，
所以「第 N 期之后的下一个场次」并不总是 `closeTime(N) + 2 days`。
三个测试都按固定天数硬算下一场次，结果 warp 到了距真实场次还有整整一天的时刻。

### T-1（Low）— 窗口抢占测试从未触发它要守的闸

`test/LotteryFieldControl.t.sol:64-84` 声称「攻击者卡在距下一场次仅 1 秒时触发」：

```solidity
uint64 nextSlot = _closeTimeOf(1) + 2 days;   // ANCHOR + 4d
vm.warp(nextSlot - 1);
…
assertGe(window, lottery.MIN_SALES_WINDOW(), "window must respect the floor");
```

但第 1 期开期时 cursor 已推进到 1，真实的下一场次由 `intervals[1] = 3 days` 决定，
是 `ANCHOR + 5d`。于是 `_openNextRound` 的 `do-while` **只跑一圈就退出**，
新期窗口是 **1 天零 1 秒**，`assertGe(window, 30 minutes)` 恒真。

把 `_openNextRound` 的 `do-while` 换成朴素的 `while (t <= block.timestamp)`
（= 把第三轮 #2 的修复整个删掉），这条测试照样绿。

- PoC（断言缺陷）：`test_Poc_WindowSnipeRegressionNeverReachesTheGuardItGuards`
  —— 实测窗口恰为 `1 days + 1`
- PoC（正确场景下防线确实有效）：`test_Evidence_RealWindowSnipeIsBlockedByMinSalesWindow`
  —— warp 到真实场次前 1 秒，新期 `closeTime` 落在**再下一个**场次，窗口 ≥ 下限

### T-2（Low）— 按比例释放的回归测试测不出它要测的 bug

`test/LotteryWindowProRata.t.sol:77-92` 是为第四轮复查 M-1 加的：
「释放比例若用百分比整数除法，正式日程的 3 天腿会算出 0%，缓冲一分不出」。

```solidity
uint64 nextSlot = _closeTimeOf(r) + 3 days;   // r = 第 2 期，但它的下一腿是 2 days
vm.warp(uint256(nextSlot) - lottery.MIN_SALES_WINDOW() - 1);
…
assertLt(_buffer(), seeded, "…must not round the release down to zero");
```

实际落到一个**跨两腿、名义 4 天、实际窗口 1 天**的组合。实测该场景下
`actual * 100 / nominal == 25`——**有 bug 的百分比实现会算出 25% 而不是 0%，
照样让这条测试通过**。

正确的场景（真正的 3 天腿 + 窗口压到下限）实测：

| 公式 | 结果 |
|---|---|
| 百分比（旧、有 bug） | `1801 * 100 / 254700 = 0` ⇒ 缓冲冻结 |
| bps（现行） | `1801 * 10000 / 254700 = 70` ⇒ 释放 0.7%，继续流动 |

- PoC（断言缺陷）：`test_Poc_ProRataRegressionDoesNotReproduceThePercentZeroCase`
- PoC（正确场景）：`test_Evidence_BpsPrecisionIsLoadBearingOnTheThreeDayLeg`
  —— 同时断言两个公式的取值，把 bps 精度是承重墙这件事钉死

同一根因还削弱了 `test_BufferDrainsEvenWithPersistentlyLateKeeper`（`:28`）：
循环里 `_closeTimeOf(r) + 2 days` 在 3 天腿上偏早一天，「窗口压到接近下限」的前提
在一半的迭代里不成立。它的断言（单调下降）仍然成立，只是比 docstring 声称的弱。

## C-1（Info）— `injectPot` 不看暂停快照

`buyTickets` 第一句就是 `if (r.salesPausedAtOpen) revert SalesArePaused();`，
`injectPot` 没有这道闸。于是全局暂停期间，任何人仍可向一个**注定卖不出任何一张票、
注定 VOID** 的期注资。

钱不会丢：VOID → `s_pendingPot` → 下一期开出时释放 → 下一期同样被暂停 → 再 VOID……
只要暂停不解除，这笔钱就在期与期之间无限循环，没有任何人能碰到它。
而 FR-C-26 明确「注入只进不出」，注资人也拿不回来。

- PoC：`test_Poc_InjectPotIgnoresTheSalesPauseSnapshot`
  （连跑 3 轮 VOID，每轮都断言钱进了下一个同样禁售的期，且偿付性恒等式成立）
- 修复方向：要么给 `injectPot` 加同一道快照闸，要么在 SPEC 里明说这是有意的
  （比如「暂停期间也允许提前把活动奖金放进缓冲」）。目前两边都没说。

## C-2（Info）— `claimTo` 的事件语义与前端统计口径

`_claim` 里 `emit PrizeClaimed(roundId, msg.sender, tier, total)` 记的是**持票人**，
不是收款地址（NatSpec 有写明，是刻意的）。副作用是
`web/app/history/page.tsx` 的「累计已领奖金」按 `PrizeClaimed.winner` 聚合，
对用了 `claimTo` 的用户显示的是**归属额**而非到账额。

- PoC：`test_Poc_ClaimToEventNamesTheHolderNotTheRecipient`
- 不建议改事件（改了会破坏奖金归属的重建）；建议在前端文案上注明，或额外把
  收款地址放进事件的非索引字段。属产品决策。

## D-3（Medium）— CI 从来没有跑过：工作流文件放错了目录

### 机制

仓库根是 `C:\test\LuckYou_2`（`origin = https://github.com/LuckyYouStudio/LuckYou_2.git`）。
全仓库唯一的工作流文件是：

```
$ git ls-files | grep workflows
contracts/.github/workflows/test.yml
$ ls .github
ls: cannot access '.github': No such file or directory
```

GitHub Actions **只**扫描仓库根目录下的 `.github/workflows/`。
子目录里的 `.github/workflows/` 会被完全忽略——它不是「作用域较小的 CI」，而是**根本不存在的 CI**。

第二个问题：即便把它挪到根目录，里面的步骤也会立刻失败——
`forge fmt --check` / `forge build` / `forge test` 必须在有 `foundry.toml` 的目录下跑，
而根目录没有。需要补 `defaults.run.working-directory: contracts`（或逐步加 `working-directory`）。

### 后果

- 从项目第一天起，`forge fmt --check`、`forge build`、`forge test` 就**没有在任何一次
  push / PR 上被强制执行过**。历史里所有「测试全绿」的结论，全部依赖开发者本地手跑。
- 这正好解释了 T-1 / T-2 能存活这么久：本地手跑只看「有没有变红」，
  而这两个测试**永远是绿的**——它们守的是自己没跑到的路径。CI 也不会发现这个，
  但一个带覆盖率/变异检查的 CI 会提高发现概率。
- R20 I-5 提的四道缺失的闸（覆盖率 ≥90%、`web` typecheck、`forge snapshot --check`、
  `npm audit`）都建立在「CI 已经在跑基础三项」这个前提上——**这个前提不成立**。

### 我没能验证的部分

`gh` CLI 在本机不可用，我**无法查询 Actions API 确认「零次运行」**。
上面的结论是从 GitHub Actions 的工作流发现规则（只读仓库根 `.github/workflows/`）
与目录结构推出的。请在仓库页面的 Actions 标签页核对一眼——如果那里空空如也，就坐实了。

### 修复方向

```
git mv contracts/.github/workflows/test.yml .github/workflows/test.yml
```
并在 `jobs.check` 下加：
```yaml
    defaults:
      run:
        working-directory: contracts
```
挪好之后再谈 R20 I-5 的那四道闸。
