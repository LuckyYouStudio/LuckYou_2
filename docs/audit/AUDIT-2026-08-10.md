## A（High）— `rolloverExpired` 绕过封盘时间闸

### 问题

自查 #5 把 `injectPot` 挡在 `closeTime` 之后，理由写得很清楚：
**「封盘后不得再改变本期奖池规模」**。但这条规则只堵了一个入口。
另一条同样「往当前期奖池打钱」的路径完全敞开：

```solidity
// Lottery.sol:418-419
uint32 target = s_currentRound;
s_rounds[target].pot += unclaimed;   // 无任何 closeTime 检查
```

`rolloverExpired` 任何人可调、**调用时机完全由调用者决定**，而 `s_currentRound`
在封盘期（`closeTime` ~ `drawTime`，长达 75 分钟）仍是 OPEN 状态。
`fulfillRandomWords` 里的 `s_rounds[target].tier1Carry += carryOut`（第 359 行）同理。

### 为什么这把「经济风险」变成了「确定性攻击」

自查 #2 已经指出「单一大户可整包捕获注资奖池」，但把它定性为待决策的经济设计。
关键差别在于：**#2 是一场赌博，加上时机自由裁量后就变成了无风险套利。**

没有这个缺陷时，攻击者必须在 `closeTime` **之前**就把过期奖金滚进来，
此时他不知道最终会有多少人跟着买票，可能被别人分走。

有了这个缺陷，攻击流程变成：

1. 每期花 8 USDC 买 8 张票（恰好覆盖默认配置的全部 8 个中奖 slot）
2. 到 `closeTime`，**票已定死**，链上公开可查自己是否是唯一买家
3. 是 → 调 `rolloverExpired(旧期)`，把整包过期奖金砸进这一期，必中全部奖级
4. 否 → 什么都不做，等下一期重来（成本仅 8 USDC 的 1% 手续费）

期望值恒为正，且第 3 步的收益是**确定的**，不是概率的。

### PoC 实测

`test_PoC_RolloverExpiredBypassesSealGate`：

```
bob spent  (USDC): 8.000000
bob won    (USDC): 17.820000
net profit (USDC): 9.820000
```

同一个测试里做了对照：**同一时刻** `injectPot` 被 `SalesClosed` 拒绝，
`rolloverExpired` 却畅通无阻——同样是往本期奖池打钱，两条路一堵一开。

### 建议修复

把「封盘后奖池规模冻结」提升为合约级不变量，而不是逐个入口打补丁。
最小改动是引入待分配缓冲区，由 `_openNextRound` 消费：

```solidity
uint256 private s_pendingCarryPot;
uint256 private s_pendingCarryTier1;

function _creditCarry(uint256 potAmt, uint256 tier1Amt) private returns (uint32 target) {
    Round storage cur = s_rounds[s_currentRound];
    // 只有仍在售票的期才能接收；已封盘则挂账，由下一期开启时承接
    if (cur.state == RoundState.OPEN && block.timestamp < cur.closeTime) {
        cur.pot += potAmt;
        cur.tier1Carry += tier1Amt;
        return s_currentRound;
    }
    s_pendingCarryPot += potAmt;
    s_pendingCarryTier1 += tier1Amt;
    return 0; // 事件里用 0 表示「挂账待下期」
}
```

`_openNextRound` 开头把挂账清零并计入新期。`rolloverExpired` 与 `fulfillRandomWords`
的 carry 都改走 `_creditCarry`。这样攻击者无论何时调用，钱都只会进入一个**尚未封盘**
的期，他必须在买票截止前做决定，赌博性质回归。

回归测试：封盘期调 `rolloverExpired`，断言当前期 pot 不变、下一期开启后 pot 增加。

## B（Medium）— `retryDraw` 让 VRF 结果变成可选择的

### 问题

```solidity
// Lottery.sol:326
if (r.state != RoundState.DRAWING || r.vrfRequestId != requestId) return;
```

`retryDraw` 会覆写 `r.vrfRequestId`，于是**上一次请求的回调被永久作废**。
FR-C-15 的本意是「旧回调不能改写已定结果」，但这里的实现顺手加上了
「旧回调不能定出结果」——两者不是一回事。

后果：一旦某期在 DRAWING 停留超过 `DRAW_TIMEOUT`（3 小时），
任何人都获得了一个**待价而沽的重摇期权**：看到即将落地的回调对自己不利，
抢在它前面调 `retryDraw`，这次开奖就作废，换一个新种子重来。
每 3 小时可以重摇一次，直到出现自己满意的结果。

这直接抵触 FR-C-11 对随机数不可操纵的要求——随机数本身没被预测，
但**「接受哪一次随机数」变成了可选的**，效果等价。

### PoC 实测

`test_PoC_RetryDrawRerollsUnfavorableOutcome`：alice 持 100 张、bob 持 1 张。
bob 抢先 `retryDraw` 作废了让 alice 中奖的那次回调（断言该回调落地后本期仍是 DRAWING），
换来的新种子让 bob 中了一等奖并成功 `claim`。

### 缓解因素

- 需要该期 VRF 回调延迟超过 3 小时，健康状态下不会发生
- 需要看得见待处理的回调交易。Base 目前是单一 sequencer + 私有内存池，
  普通攻击者很难抢跑；但这条护城河来自**链的实现细节**，不是合约的安全属性，
  换链或 Base 未来开放内存池即失效

因此定 Medium 而非 High，但修复成本极低，建议直接改掉而不是依赖链的特性。

### 建议修复

不作废旧请求，改成**先到先得**——任何映射到本期的请求都可以定出结果，
本期一旦 SETTLED 后续回调自然被 state 闸拦下（FR-C-15 依然满足）：

```solidity
uint32 roundId = s_requestToRound[requestId];
if (roundId == 0) return;                              // 未知 requestId
Round storage r = s_rounds[roundId];
if (r.state != RoundState.DRAWING) return;             // 已结算/已作废，静默丢弃
```

`s_requestToRound` 本来就从不清理，旧请求的映射仍在，改动只需删掉
`r.vrfRequestId != requestId` 这半个条件。`r.vrfRequestId` 保留给
`retryDraw` 的超时计时与前端展示即可。

回归测试：请求 A 超时后 `retryDraw` 得到 B，随后 A 的回调落地——断言本期正常结算。

## C（Medium）— VRF 订阅所有者是未披露的信任方

FR-C-22 详尽列举了 owner 的权限面（这份清单写得很好），但漏了一个**合约外**的角色：
`i_subId` 对应的 VRF 订阅所有者。该角色可以：

- `removeConsumer(subId, lottery)` → `_requestRandomWords` 全部 revert
  → `performUpkeep` 与 `retryDraw` 双双失效，当前期永远卡在 OPEN，
    已进入 DRAWING 的期奖池**永久冻结**
- 撤走订阅里的 LINK → 同样效果

这不是资金被盗（没有出口能把奖池转给他），但**足以永久冻结所有未结算奖池**，
而合约里不存在任何解冻手段（FR-C-24 明确禁止 `emergencyWithdraw`，这是对的）。

测试网上订阅所有者就是部署者本人，等于 owner 权限被低估了一档。

**建议**：在 FR-C-22 与合约 NatSpec 里显式披露这条信任假设，与 `setCoordinator`
那条并列。主网前把订阅所有权移交多签。合约本身无需改动——这是治理问题，
但必须写进文档，否则「owner 业务权限仅限三项」的表述是误导性的。

## D（Low）— `WinnersPicked` 缺 tier 映射，FR-C-25 不成立

事件只发出一个稠密数组：

```solidity
event WinnersPicked(uint32 indexed roundId, uint32[] winningTickets, address[] winners);
```

而 `_deriveWinners` **跳过了未开出的奖级**（`s_perWinnerAmount == 0` 的 tier）。
于是数组下标 → 奖级的映射依赖「哪些 tier 开出了」，而这个信息**没有任何事件承载**——
它只存在于 `s_perWinnerAmount` 存储里。

FR-C-25 要求「索引字段足以让前端仅靠事件重建全部历史」，这一条因此不成立。

前端已经踩到了这个坑（`web/app/page.tsx:302-312`）：

```ts
const slotTier = useCallback((slot: number): number => {
  let acc = 0;
  for (let t = 0; t < tierWinners.length; t++) {
    acc += tierWinners[t];
    if (slot < acc) return t;    // 假设所有奖级都开出了
  }
  ...
```

默认配置 `[1,2,5]` 下 tier0 只需 1 张票、恒定开出，未开出的永远是尾部奖级，
所以**当前不可复现**。但构造器接受任意奖级配置（如 `counts = [3,1]`，
2 张票时 tier0 关闭而 tier1 开出），届时前端会把二等奖标成一等奖。

**建议**：事件里带上 slot 或 tier 信息，例如
`WinnersPicked(uint32 indexed roundId, uint8[] slots, uint32[] winningTickets, address[] winners)`，
前端改为按 slot 反查奖级。

## E（Low）— 前端硬编码票价与精度

FR-C-01 明确要求合约不假设 token 精度，合约做到了；但前端把这个假设又加了回来：

- `web/app/page.tsx:47` `fmt6()` 写死 `/ 1e6`
- `web/app/page.tsx:293` `BigInt(n) * 1_000_000n` —— 写死票价 1 USDC
- `web/app/history/page.tsx:105,173` 同样写死

`cost` 是用来算 `approve` 额度的。一旦部署时 `i_ticketPrice` 或 token 精度变化，
授权额度就会算错，购票交易直接失败。

**建议**：从合约读 `i_ticketPrice` 与 token 的 `decimals()`，在 `contracts.ts` 里
统一导出（与 FR-W-07「单一配置出口」一致）。

## F（Low）— 无界 view 循环被高频调用

`ticketsOwned`（第 561 行）与 `getRanges`（第 556 行）都是对 `s_ranges[roundId]`
的全量线性遍历，无分页、无上限。前端每 10 秒调一次 `getRanges(cur)`，
并对最近 8 期各调一次 `ticketsOwned`。

单期 Range 条数达到几千时，`eth_call` 会先撞公共 RPC 的 gas/超时限制，
前端整个刷新循环进入 `catch` 分支，界面停止更新。链上资金无风险，但可用性会先崩。

**建议**：`getRanges` 加 `(offset, limit)` 分页；前端的「我的持票」改为从
`TicketsBought` 事件累加（FR-W-03 本来就要求走事件）。

## G（Low）— 覆盖率口径与 `ReceiverTemplate` 的空白

`src/Lottery.sol` 行覆盖 99.26%，完全达标。但 `forge coverage` 的整体数字是 **64.38%**，
低于 FR-T-01 的 ≥90%，缺口几乎全在 `src/cre/ReceiverTemplate.sol`（13.89%）。

这是 Chainlink 官方模板代码，但它**确实被部署上链**，而且带 `onlyOwner` 的
`setForwarderAddress(address(0))`——调用后 `onReport` 变成任何人可调
（模板自己 emit 了 `SecurityWarning("...now INSECURE")`）。

好在 `performUpkeep` 本就无权限，桥接器不引入新权限面，自查这个判断是对的，
**没有实际风险**。但零覆盖的已部署代码是审计红线，且 FR-T-01 的字面要求未满足。

**建议**：补 `ReceiverTemplate` 的权限分支测试（forwarder 校验、workflowId/author 校验、
设为 0 后的行为），或在 SPEC 里把 FR-T-01 的口径明确限定为 `src/Lottery.sol`。

## H（Low）— 售票窗口可被配置成近乎为零

```solidity
if (intervals[i] <= SEAL_GAP) revert InvalidSchedule();   // 只要求 > 75 分钟
```

若某个间隔配成 76 分钟，则上一期在 `closeTime + 75min` 开奖，
下一期的 `closeTime` 只比这一刻晚 60 秒——`_openNextRound` 开出的新期
只有 1 分钟售票时间。`Deploy.s.sol` 的 `FAST_INTERVAL_SECONDS` 分支
只在注释里提示「须 > 75 分钟」，没有下限校验。

**建议**：把校验收紧为 `intervals[i] <= SEAL_GAP + MIN_SALES_WINDOW`
（`MIN_SALES_WINDOW` 取 1 小时之类的 constant）。

## 复核确认**没有**问题的点

在上一轮自查的基础上，我重新独立验算了以下部分，结论一致：

- **`setCoordinator` 修复完备**：`_requestRandomWords` 恒发往 `i_coordinator`，
  回调开头强制 `address(s_vrfCoordinator) == i_coordinator`。owner 换源后
  真 coordinator 的回调会被基类 `onlyCoordinator` 拒、假 coordinator 的回调
  会被 `CoordinatorTampered` 拒——两条路都堵死，且 owner 换回即恢复
- **滚存守恒**：`distributed + carryOut == pot + tier1Carry` 逐项重算无泄漏；
  比例舍入 dust（`pot - splitTotal`）与均分余数（`amount % winners`）都并入 carryOut
- **结算期 `r.pot` 不清零不构成重复计账**：结算后付款走 `perWinnerAmount`，
  `r.pot` 仅作历史展示；`invariant_SolvencyExact` 对 SETTLED 期只计
  `_unclaimedOf` 而不计 pot，口径正确
- **二分查找**：Range 连续分区不重不漏，`_ownerOfTicket` 找的是首个 `end > ticketId`
  的区间，边界正确；空数组下溢路径经三处调用点确认不可达
- **claim 与 rolloverExpired 时间窗互斥**：`<=` 与 `>` 严格互补，无重叠、无空隙；
  per-slot 位图杜绝重复领取；CEI + `nonReentrant` 到位
- **DRAWING 期奖池冻结**：`buyTickets`/`injectPot` 都要求 state == OPEN，
  `rolloverExpired`/carry 都打向 `s_currentRound`（永远不是正在开奖的那期），
  因此种子产生后本期 pot 不可能再变（问题 A 影响的是**封盘期**的期，不是 DRAWING 期）
- **`_lastTuesdayNoonUtc`**：纪元周四基准、`(d%7+7-5)%7` 回退天数、
  周二 12:00 未到时减 7 天——三个分支逐个验算正确；`[2,3,2]` 间隔确实产出周二/四/日
- **链上地址**：Base Sepolia / Base 主网的 VRF v2.5 coordinator 与 Circle USDC
  地址与官方文档一致
- **无原生币入口**（FR-C-03）、**无资金后门**（FR-C-24）：确认合约内资金出口
  只有 `claim`（中奖者）与 `withdrawFees`（只到 treasury）两条

## 结论与优先级

**上主网前必须处理**：A、B（都是小改动，配回归测试）；C 必须至少写进文档并把
VRF 订阅所有权移交多签。

**建议一并处理**：D（改事件结构会影响前端，越早越省事）、E、G。

**运维层面**：当前 owner = 部署者 = treasury = 同一个 EOA
（`0xA7b4…743f`）。这在测试网无所谓，但主网上它同时是合约 owner、
VRF 订阅所有者、抽成收款人和 CRE 接收器 owner——**单点私钥即全局风险**，
其严重性超过本报告里的任何一条代码问题。

本报告是独立代码审计，**不能替代第三方专业审计**。SPEC 第 9 节 Q7
的合规评估（牌照、运营主体辖区）与本报告无关，仍需独立完成。
