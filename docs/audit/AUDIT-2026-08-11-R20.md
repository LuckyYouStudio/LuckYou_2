## H-1（High）— VRF 订阅迁移会永久冻结整台机器

### 机制

第一轮审计的 Critical 修复是：把 coordinator 钉死成 `immutable i_coordinator`，
请求只发往它，回调强制 `address(s_vrfCoordinator) == i_coordinator`，
否则 `revert CoordinatorTampered`。目的是封住 owner 用继承来的 `setCoordinator` 换源操纵开奖。

问题在于 `setCoordinator` 的修饰符不是 `onlyOwner`，而是 **`onlyOwnerOrCoordinator`**：

```solidity
// VRFConsumerBaseV2Plus.sol:150
function setCoordinator(address _vrfCoordinator) external override onlyOwnerOrCoordinator {
```

而 `VRFCoordinatorV2_5.migrate(subId, newCoordinator)`（**订阅所有者**可调，不是彩票 owner）
正是这样用它的：

```solidity
// VRFCoordinatorV2_5.sol:751-789
function migrate(uint256 subId, address newCoordinator) external nonReentrant {
    ...
    _deleteSubscription(subId);                                  // ← 旧源不再认这个订阅
    IVRFCoordinatorV2PlusMigration(newCoordinator).onMigration{value: nativeBalance}(encodedData);
    ...
    for (uint256 i = 0; i < consumersLength; ++i) {
        IVRFMigratableConsumerV2Plus(consumers[i]).setCoordinator(newCoordinator); // ← 改我们的 s_vrfCoordinator
    }
}
```

迁移完成后，合约两条腿同时断：

| 路径 | 结果 |
|---|---|
| 回调 | 新 coordinator 是合法随机源，但 `s_vrfCoordinator != i_coordinator` → **恒 revert `CoordinatorTampered`** |
| 请求 | `_requestRandomWords` 恒发往 `i_coordinator`，而那里的 `subId` 已被删除 → 请求 revert |

`performUpkeep` 里的 try/catch（第十轮 #1 的修复）在这里反而放大了后果：
请求失败被吞掉、只 emit `DrawRequestFailed`，于是**新期照常开出、照常收钱**，
但一期也结算不了。`retryDraw` 同样救不回来。

### 后果

- 迁移瞬间起，每一期都停在 DRAWING；`claim` 要求 SETTLED，所以**所有奖池永久冻结**
- 彩票不会「停摆报错」，它会继续正常售票——**用户还在往一个黑洞里付钱**
- FR-C-24 禁止任何 `emergencyWithdraw`/`sweep`，合约里没有出口
- `i_coordinator` 是 immutable，**没有任何办法重新钉死**

### 为什么这不是「理论风险」

1. 迁移的触发者是**订阅所有者**，不是彩票 owner——即使彩票 owner 是多签、私钥安全，
   这条路依然开着
2. Chainlink 有强制迁移的先例：本项目自己就因为 **Automation 被官方弃用**（SPEC Q8）
   才改用 CRE。VRF v2.5 将来同样会有下一代 coordinator，届时迁移不是选项而是义务
3. SPEC FR-C-22/24 目前的措辞是「owner 换源无法操纵开奖或挪用资金，最坏只能造成
   **可自行恢复的结算延迟**」——对合法迁移这一情形，这句话是错的

### PoC

`test/AuditR20Poc.t.sol`：
- `test_Poc_H1_MigrationFreezesInFlightRound` —— 100 张票（0.01 ETH）在 DRAWING 期冻结，
  真回调被拒、`retryDraw` revert、`claim` revert
- `test_Poc_H1_MigratedLotteryKeepsTakingMoneyAndNeverSettles` —— 连开 3 期、每期都收钱、
  `s_currentRound` 推进到 4，`vrfRequestOf` 全为 0，99% 的票款不可达

### 修复方向（需要 SPEC 层决策，未擅自实现）

**A. 立刻可做、零代码改动（无论如何都要做）**

把「VRF 订阅所有者**绝不可调用 `migrate`**」写进 FR-C-24 的外部信任方清单，
与已有的「不可 `removeConsumer`」并列，并把订阅所有者设为多签。
注意这只是把风险转成运营纪律，**并不能应对 Chainlink 强制迁移**。

**B. 结构性修复（建议主网前落地）：把防线从「钉死地址」搬到「owner 的能力」**

`setCoordinator` 无法 `override`（非 `virtual`），但可以让 `owner()` **物理上没有能力调它**：
把 Lottery 的 owner 移交给一个极小的、不可升级的 `LotteryAdmin`，它**只**转发
`setTreasury` / `setFeeBps` / `setSalesPaused`，**不含**任何通用 `execute(address,bytes)`
路径、也**不含** `transferOwnership`。此后 `setCoordinator` 只剩 coordinator 自己能调
（= 只有合法迁移），于是可以：

- `_requestRandomWords` 改用 `s_vrfCoordinator`（跟随迁移）
- 回调里的 `CoordinatorTampered` 校验可以去掉

代价必须说清楚：**owner 权限从此永久绑定在那个合约上**，`LotteryAdmin` 若有 bug，
三项业务权限一起失去（但奖池不受影响——它们本来就动不了奖池）。
这条路把 H-1 和 M-2 一次解决，且不引入代理、不引入行政提款，符合 FR-C-24 的立意。

**C. 兜底逃生通道（SPEC FR-C-24 自己已经点出「主网前应当评估」的那条）**

`abandonStuckRound(roundId)`：某期在 DRAWING 停留超过某个长阈值（如 30 天）后，
任何人可将其标记为可退款，购票者按 `票价 × 张数` pull 式原路取回，
carry 部分退回缓冲区。**不含任何自由裁量权**，因此不违反 FR-C-24 的禁令
（该条禁的是「管理员能动到未领奖金」）。
注意还需要一条对应的缓冲区逃生规则，否则 `s_pendingPot` / `s_pendingTier1`
在同一场景下仍然出不来。

我的建议是 **A + B**，把 C 作为独立议题评估——A 是纪律，B 才是消除杠杆。

## H-2（High，经济设计）— 配比门槛的资本可以循环复用

### SPEC 现在的说法

> 现行配比制使资本门槛与捕获量线性挂钩……配比只抬高资本门槛（**投 X 至多撬动 X 的 carry**）
> 并给其他参与者稀释的机会

读起来像是：要吃下 10 ETH 的 carry，就得备齐 10 ETH。

### 实际情况

攻击者的本金**随中奖立刻回到自己手里**，所以同一笔钱每期复用一次。
每期净收益 ≈ 本金（只损耗 1% 抽成）。实测（`test_Poc_H2_SoleBuyerRecyclesCapitalToDrainBuffer`）：

| | |
|---|---|
| 运营方冷启动注资 | 10 ETH |
| 攻击者本金 | **1 ETH** |
| 单期投入 → 产出 | 1 ETH → **1.98 ETH**（净 +0.98） |
| 一期后缓冲余额 | 9.01 ETH，等着下一期用同一笔钱再抽一次 |

按官方日程（每周二/四/日）约 3 周即可把 10 ETH 抽干，**资本占用恒为 1 ETH**。

### 为什么是零风险而不只是 +EV

关键是「唯一买家」这件事可以**在链上强制**，不必靠运气：

```solidity
function buyOnlyIfEmpty(uint32 roundId, ...) external {
    (,,, uint32 ticketCount,,,,,) = lottery.getRound(roundId);
    if (ticketCount != 0) revert NotSoleBuyer();   // 有人买过就整笔回滚，白付 gas 而已
    ...
}
```

停售前最后一刻发这笔交易：若已有他人参与则交易回滚、攻击者零损失；
若无人参与则他独占全场、必中所有奖级。既有的 30 分钟最短窗口、按窗口打折、
1:1 配比**都不影响**这个策略——它们限制的是单期捕获量，而不是重复次数。

### 诚实的边界

- **前提是有效参与度接近零**。任何人买 1 张票就会让上面那笔交易回滚。
  也就是说：这不是「攻击一个热闹的彩票」，而是「碰上一个冷清的彩票 + 一笔大额注资」——
  而这恰好就是冷启动注资（Q6/FR-C-26）的典型场景
- 即使不做唯一买家，任何份额都是 +EV（carry 是白送的补贴），所以健康状态下
  carry 会被正常参与者按份额分掉——那是**设计意图**，不是缺陷

### 建议

1. **改 SPEC 措辞**（必须）：删掉/修正「投 X 至多撬动 X 的 carry」这类暗示资本门槛
   等于 carry 规模的表述，写明「本金可逐期复用，暴露面是整包缓冲，单期成本仅为抽成」
2. **运营纪律**（可立刻执行、最有效）：**单次注资不要超过一期有机售票额的量级**。
   缓冲区规模一旦远大于自然成交量，上面的策略就必然有利可图。
   把「大额冷启动」拆成多期小额注入，或干脆等有机成交量上来再注
3. 若要在代码上再压一档：把 `CARRY_MATCH_MULTIPLIER` 降到 1 以下（需要改成 bps 表达），
   把单期净收益从 ≈100% 压到 ≈50%。**这不能消除策略**，只是把抽干时间拉长一倍——
   要不要付这个「正常参与者拿到的 carry 也一起减半」的代价，是产品决策

## M-1（Medium）— 不能收原生币的合约钱包，中奖即等于弃奖

`buyTickets` 对调用方没有任何要求，但 `claim` 走 `_sendValue` → `call{value:}`，
收款方没有 `receive`/`fallback` 就 `revert TransferFailed`。

实测（`test_Poc_M1_NonPayableWinnerCannotClaim`）：一个只写了 `buy`/`claim`、
没写 `receive` 的合约钱包买光全场、确定中一等奖，`pendingPrizes` 显示可领 `5.94e14`，
但 `claim` **恒 revert**，90 天后被 `rolloverExpired` 扫进缓冲区。

这是 2026-08-11 原生 ETH 改造新增的攻击面：ERC20 时代转账到任何地址都成功。
FR-C-22 只为 **treasury** 记录了这条新约束，**没有为购票者记录**。
`_sendValue` 的 NatSpec 也只提到「多签等合约钱包收不到款」（说的是 2300 gas 上限），
恰好漏掉了「根本没有 payable 入口」这一类。

**建议**（二选一或都做）：

- 低成本：在 NatSpec / 前端 / README 明确「合约钱包必须能接收原生币」
- 更好：加 `claimTo(uint32 roundId, uint8 tier, address to)`。只有中奖票的持有人能调，
  仍是 CEI + `nonReentrant`，把收款地址与持票地址解耦。这既救了非 payable 合约钱包，
  也顺手解决「冷钱包持票、想直接领到热钱包」的正常需求。
  不增加权限面（钱只能由票主自己指向别处）

## M-2（Medium）— owner 私钥被盗 = 不可恢复的全局冻结

M-2 与 H-1 同源但触发者不同。SPEC FR-C-22 的现有措辞：

> owner 换源无法操纵开奖或挪用资金，最坏只能造成**可自行恢复**的结算延迟

「可自行恢复」的前提是 owner 还能操作。若私钥丢失或被恶意方持有：

- 攻击者调一次 `setCoordinator`（任意地址）→ 此后所有回调 `CoordinatorTampered`
- 请求虽然仍发往钉死的 coordinator 且能成功，但**回调永远落不了地**
- 每次回调失败都白烧一次 LINK；任何人可每 3 小时 `retryDraw` 继续烧
- 合约没有 `renounceOwnership`、没有办法把 `setCoordinator` 焊死，**无法恢复**

偷不到钱，但能让所有人的钱永远出不来——对彩票用户而言两者的差别不大。

**建议**：owner 用多签（这是必须的，但只降低概率）；根本解法同 H-1 的方案 B——
把 owner 换成没有 `setCoordinator` 能力的合约，这条杠杆就从物理上消失了。

## M-3（Medium）— 卡死的期没有任何自动兜底（第一轮遗留 #3，至今未闭环）

- `checkUpkeep` 只看 `s_currentRound`，而 `s_currentRound` 恒为 OPEN（`_openNextRound` 保证），
  所以它**永远不会**为一个卡在 DRAWING 的旧期返回 true
- CRE 工作流（`keeper-cre/luckyou-keeper/workflow.ts`）只做 `checkUpkeep → performUpkeep`，
  完全没有 `retryDraw` 的路径
- `LotteryKeeperReceiver._processReport` 也只转发 `performUpkeep`

结果：只要有一期因为任何原因（LINK 耗尽、`removeConsumer`、回调 revert）卡住，
就必须有人**手工**发现并调 `retryDraw`。前端有个「重试第 N 期 VRF」按钮，
但只在用户打开页面且该期落在显示的 8 期内时才出现。

`retryDraw` 本来就是无权限的，所以自动化它**不引入任何新的信任**。

**建议**（选一个）：

- 扩 CRE 工作流：链下扫最近 N 期，遇到 `DRAWING && now > drawRequestedAt + DRAW_TIMEOUT`
  就投递一份带 roundId 的报告；`LotteryKeeperReceiver` 增加对应分支
- 或让 `performUpkeep` 使用它现在完全忽略的 `performData`：解出一个 roundId，
  若该期确实 DRAWING 且已超时就顺手重试一次。`performData` 不可信没关系——
  这条路径本来任何人都能走，闸门在合约里

## L-1 — `buyTickets` 缺 `roundId` 闸

`injectPot(uint32 roundId)` 有期号闸，`buyTickets(uint32 quantity)` 没有。
一笔在第 N 期发出、但直到 `performUpkeep` 之后（≥ `SEAL_GAP` = 75 分钟）才上链的交易，
会**静默地**买进第 N+1 期——用户看到的奖池、倒计时、已售票数全都不是他实际买到的那一期。

实测：`test_Poc_L1_DelayedBuyLandsInNextRound`（bob 在他看到的期里 0 张，下一期 5 张）。

75 分钟的延迟在正常链况下不常见，但 gas 定价过低的交易可以在 mempool 里待很久。
`injectPot` 已经有这个闸，说明这个风险在设计时被认识到了，只是没同步到 `buyTickets`。

**建议**：`buyTickets(uint32 quantity, uint32 expectedRoundId)`，不匹配就 revert。
这会改动 FR-C-04/09 的函数签名与前端，属于 SPEC 变更，故未擅自实施。

## L-2 — 前端 `CLAIM_SCAN_ROUNDS` 的推导算错了 9 倍

```ts
// 领奖窗口 90 天；按最短场次间隔（快节奏实例 2 小时）反推需回溯的期数上限，
// 避免中奖者因界面只看最近几期而错失奖金（审计第九轮 C1）
const CLAIM_SCAN_ROUNDS = 120;
```

注释声称的推导是「90 天 ÷ 2 小时」，那应该是 **1080** 期，不是 120。
120 期 × 2 小时 = **10 天**。

- 官方日程（平均 2.33 天/期）：90 天 ≈ 39 期，120 足够 —— 主网不受影响
- 快节奏测试网实例（`FAST_INTERVAL_SECONDS`，`LocalTestbed` 用 2 小时）：
  中奖者在第 11 天起就再也看不到自己的奖金提示，而链上窗口还有 80 天

这个数字正是第九轮为「别让中奖者错失奖金」专门加的防线，值得订正。

**建议**：不要写死期数——按链上 `claimDeadlineOf` 反推（从 `s_currentRound` 往回扫，
一旦某期的 `settledAt + CLAIM_WINDOW` 已经过期就停止），或至少把常量提到 1200。

## L-3 — `history` 页的事件扫描随链长线性增长

```ts
for (let from = startBlock; from <= latest; from += BLOCK_CHUNK + 1n) {   // BLOCK_CHUNK = 9000
  await publicClient.getLogs({ ... });   // TicketsBought
  await publicClient.getLogs({ ... });   // PrizeClaimed
}
```

两次 `getLogs` **串行** `await`，且循环从部署块一直扫到链头。
Base Sepolia 出块 2 秒 ⇒ 每年 ~1576 万块 ⇒ 一年后每次打开页面约 **3500 次串行 RPC**。
按公共 RPC 150ms 延迟算 ≈ 9 分钟，且几乎必然先被限流打断（catch 后只显示「加载失败」）。

FR-W-03 要求「历史一律从链上事件读取」，实现是对的，但**规模不可持续**。

**建议**：把每段的两次 `getLogs` 合并进 `Promise.all`，并对分段做并发（如 8 路）；
更根本的做法是从链头**倒序**扫、拿满一屏就停，配合「加载更多」。
不需要后端，也不违反 FR-C-1.2 的「不做后端数据库」。

## L-4 — `anchorTime` 不受校验，远古锚点会让部署 OOG

构造器只校验 `intervals[i] > SEAL_GAP + MIN_SALES_WINDOW`，不校验 `anchorTime`
与 `block.timestamp` 的距离。`_openNextRound` 的追赶循环从 `anchorTime` 起一格一格推进：

实测 `anchor = 1`、`interval = 6301`（合约允许的最小值）时，部署需 **207.9M gas** → 必然 OOG。

不是资金风险（配错就部署不出来，失败得很响），但它是一个**一次性、不可修复**的配置项
（日程全合约无 setter），值得一道显式闸。

**建议**：`if (anchorTime + intervals[0] + 365 days < block.timestamp) revert InvalidSchedule();`

顺带用同一组实测**关闭**第一轮的 Info #9（「追赶循环理论无界」）：
官方 `[2,3,2]` 天日程下，停摆后首次 `performUpkeep` 的实测 gas 为

| 停摆时长 | 1 年 | 5 年 | 20 年 | 50 年 | 100 年 |
|---|---|---|---|---|---|
| gas | 342k | 837k | 2.69M | 6.40M | 12.6M |

即使停摆 100 年也远低于区块上限。**结论：这不是 DoS，可以结案。**

## Info 级

- **I-1** `_withholdExcessCarry` 对同一笔钱同时 emit `CarryWithheld` 和 `PrizeRolledOver`。
  按 FR-C-25 做纯事件重建的索引器若把两者都算作缓冲区流入，会**重复计数**。
  建议在 `PrizeRolledOver` 的 NatSpec 里点明「`CarryWithheld` 是同一笔钱的附加说明，勿累加」
- **I-2** 构造器拒绝 `tierWinnerCounts[i] == 0`，但**接受** `tierBps[i] == 0`。
  这样的奖级 `perWinner` 恒为 0 ⇒ 永远判为「未开出」⇒ 每期把它那份滚走，
  却照样占用 16 个 slot 的名额预算。建议一并拒绝
- **I-3** `_ownerOfTicket` 的 `hi = ranges.length - 1` 在空数组时下溢 panic。
  当前**所有**调用点都被 `state == SETTLED`（⇒ `ticketCount ≥ 1` ⇒ `ranges ≥ 1`）
  或 `ticketId < ticketCount` 挡住，实际不可达。但这个前置条件没有任何注释或断言固定住，
  将来新增一个视图函数就可能踩上。建议加一行注释说明不变量
- **I-4** `ReceiverTemplate.sol` 行覆盖 **13.89%**、pragma 用 `^0.8.0`（项目规范要求固定 `0.8.26`）、
  `_decodeMetadata` 用裸 assembly 读 `metadata` 且不校验长度。它是 Chainlink 官方模板的
  vendored 副本，且默认配置下三个 `s_expected*` 全为零 ⇒ `_decodeMetadata` 根本不会被调用，
  唯一生效的闸是 forwarder 地址。风险可接受，但**应当在 SPEC 里显式写「按原样接受上游模板，
  不计入 FR-T-01 覆盖率口径」**，否则每轮审计都会重新报一次（前三轮已报过两次）
- **I-5** CI（`.github/workflows/test.yml`）只跑 `fmt` / `build` / `test`。缺：
  ① `forge coverage` 的 ≥90% 闸（FR-T-01 是硬性要求，现在靠人工核对）
  ② `cd web && npm ci && npx tsc --noEmit`（CLAUDE.md 要求「改完必跑」，但没有自动化）
  ③ `forge snapshot --check`（`.gas-snapshot` 已入库却无人校验）
  ④ `npm audit`（见 L-5）
- **I-6** SPEC 多处仍是 ERC20 时代的措辞，与已被 FR-C-01 推翻的现实冲突：
  FR-C-26 写 `injectPot(uint32 roundId, uint256 amount)` 且「SafeERC20 收款」（实际是 `payable`）、
  FR-W-02 整条在讲 `approve` 两步流程（已不存在）、FR-T-02「两种 decimals 的 token」、
  FR-T-03「合约 token 余额」、FR-T-04「用恶意 ERC20 回调」。
  SPEC 自称「唯一事实来源」，这类失效措辞比代码 bug 更容易误导后续开发
- **I-7** `keeper-cre/luckyou-keeper/workflow.ts` 里 `getNetwork({ ..., isTestnet: true })` 是硬编码的，
  而 `config.production.json` 的 `chainSelectorName` 也确实是 Base Sepolia。
  目前自洽，但「production」这个命名会让上主网时很容易漏掉这一行

## 20 个视角的逐条结论

已在上面给出缺陷的视角不再重复，以下是**复核确认没有问题**的部分——
每条都给出判定依据，而不只是「看过了」。

| # | 视角 | 结论 |
|---|---|---|
| 1 | 规格一致性 FR-C-01~28 | 代码与规格一致；**规格自身**有失效措辞（I-6） |
| 2 | 资金守恒 / 偿付性 | 手工推导结算分账：`pot + tier1CarryIn == Σ(perWinner × winners) + carryOut` **恒等**（比例余数与均分余数都并入 `carryOut`），零泄漏；`invariant_SolvencyExact` 用的是**等式**而非不等式，2048 次调用无违反 |
