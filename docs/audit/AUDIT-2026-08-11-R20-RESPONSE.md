## H-1：我漏掉了什么，为什么会漏

我在第一轮审计里把 coordinator 钉死成 `immutable`，用来堵住「owner 换随机源、
离线挑种子稳中头奖」这个 Critical。我当时只检查了 `setCoordinator` **能被谁调用**
这个问题的一半——看到它不是 `onlyOwner` 就没再往下追。

实际是 `onlyOwnerOrCoordinator`（`VRFConsumerBaseV2Plus.sol:159`），
而 `VRFCoordinatorV2_5.migrate()`（`:751`，**订阅所有者**可调）第 785 行
正是遍历全部 consumer 逐个调 `setCoordinator`。

于是官方迁移一旦发生：回调被我自己的 `CoordinatorTampered` 判为篡改，
请求又发往已经删掉订阅的旧 coordinator——**两条腿同时断，每期卡在 DRAWING，
`retryDraw` 也救不回来，而 FR-C-24 禁止任何救援手段**。彩票不会报错停摆，
它会继续正常售票收钱。

这恰好又是我自己在上一份报告里总结的元教训的又一个实例：**为堵住 A 而加的防线，
本身成了 B**。第一轮我用「钉死」换掉了「owner 可操纵随机数」，代价是把「合法迁移」
一起钉死了——而我没意识到这个代价存在。

已做：把两条路径写进 FR-C-22 的信任方清单，订正原来那句错误的
「最坏只能造成可自行恢复的延迟」。

未做（**需要你拍板，已登记为 SPEC Q9**）：根因修复。三个候选方案的取舍写在 Q9 里，
我的建议是 **B（LotteryAdmin）+ C（逃生通道）**——B 消除杠杆，C 兜底任何原因的卡死。
这属于 CLAUDE.md 规则 6 的「SPEC 未决问题」，不自己拍板。

## L-3：比报告说的更严重——一个已经在倒计时的定时炸弹

报告指出 history 页「两次 `getLogs` 串行 + 分段串行」会随链长线性劣化。属实。
但我在浏览器里实测修复时，撞到了一个报告没提、也没人发现的**当下就会炸的 bug**：

```
BLOCK_CHUNK = 9000n   // 注释：「常见 RPC 限制在 1 万个区块以内」
```

而 `sepolia.base.org` 的 `eth_getLogs` 硬上限是 **2000 块**：

```
{"code":-32602,"message":"query exceeds max block range 2000"}
```

这个数字是想当然写的，对本项目实际使用的端点就是错的。之所以一直没暴露，
只是因为每次重新部署后合约距链头不到 2000 块——**链一往前走，「我的记录」页
就必然对所有人报错**。我这次部署后约两小时就撞上了。

顺带说明：这类 bug 靠 `typecheck` 和 `build` 一个都发现不了，两者当时都是绿的。

已修：`BLOCK_CHUNK = 1999`（`to = from + BLOCK_CHUNK` ⇒ 单段恰好 2000 块）、
段内两个事件并行、分段 8 路并发、超过 600 段时从链头倒序截断并**在界面上如实标注
「仅显示区块 N 之后的记录」**——宁可诚实地少显示，也不要静默给出不完整的历史。

浏览器实测：扫约 7000 块（4 段）成功，正确重建出 2 条购票 + 3 条领奖记录。

## M-1：`claimTo` 的设计取舍

原生币改造把「派奖」从纯记账变成了对任意代码的调用，随之带来一类新的弃奖：
没有 `receive`/`fallback` 的合约钱包中奖后 `claim` 恒 revert，90 天后奖金被扫走。

加 `claimTo(roundId, tier, to)`。关键是它**不增加任何权限面**：

- 中奖判定恒以 `msg.sender` 持票为准，`to` 只决定钱付到哪里
- 因此没有票的人指定任何 `to` 都拿不到钱（有回归测试断言这一点）
- `to` 为零地址直接 revert，避免把奖金烧掉
- 与 `claim` 共用同一份 `claimedBits` 记账，不会重复领取

顺带满足「冷钱包持票、想领到热钱包」这个正常需求。

注意 `claim` 对这类钱包**依然**会 revert——那是事实，改不了（对方确实收不了款）。
`claimTo` 提供的是一条不弃奖的出路，不是把问题掩盖掉。

## 我不打算做的，以及为什么

- **L-1（`buyTickets` 加 `expectedRoundId`）**：确实是个真实的、`injectPot`
  已经防住而 `buyTickets` 没防的不一致。但它改动 FR-C-04/09 的函数签名与全部前端调用，
  属 SPEC 变更。同时它需要重新部署合约。留待与 Q9 一起决策。
- **L-5（`next@16` 升级）**：两个 high 的可达性评估我复核后同意——本项目没有
  攻击者可控的 CSS 输入，也没用 `next/image`。为不可达的 CVE 做破坏性大版本升级
  不划算，登记跟踪，等引入相关功能时再处理。
- **CARRY_MATCH_MULTIPLIER 降到 1 以下**（H-2 的代码缓解）：它**不能消除**策略，
  只把抽干时间拉长一倍，代价是正常参与者拿到的 carry 也减半。这是产品决策不是安全修复，
  留给你定。真正有效的是 FR-C-26 里那条运营纪律。
