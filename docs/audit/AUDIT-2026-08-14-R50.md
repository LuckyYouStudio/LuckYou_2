## A-1（Medium）— `withdrawFees` 是一个人人可拉的断路器

### 机制

`_accrueKeeperReward` 的三道夹逼里，第三道是「不超过当下实际尚存的 `s_accruedFees`」——
它本来只是**防下溢**。但 `withdrawFees`：

- **无权限**（任何人可调，钱只会去 treasury，所以此前没人觉得它是攻击面）；
- **全额**清空 `s_accruedFees`；
- 约 3 万 gas。

于是任何人只要在**封盘期**（`closeTime` → `closeTime + SEAL_GAP` 之间的 75 分钟，
此时售票已停、抽成不会再增加）调一次 `withdrawFees()`，该期的开奖奖励就恒为 0。

**这里不需要抢跑，也不需要和 keeper 竞速** —— 有整整 75 分钟的窗口，
而且此后到 `performUpkeep` 之前不会有任何新抽成进账。

### 后果

FR-C-30 存在的全部意义是「运营方缺席时仍有人有理由接手按按钮」。
一个 3 万 gas 的操作就能把这个安全网逐期摘掉，而且攻击者不需要有任何收益动机
（钱进的是 treasury，不是攻击者口袋）—— 纯骚扰的成本低到可以忽略。

**更可能发生的是非对抗版本**：运营方自己例行调一次 `withdrawFees` 提走抽成，
就无意中把当期奖励清零了。谁也不会想到「提自己的钱」会关掉 keeper 激励。

### PoC

`test/AuditR50Poc.t.sol`（修复前的断言）：

```
_buy(alice, 500)              → pendingKeeperReward(1) == PRICE（满额）
bob 调 withdrawFees()          → s_accruedFees == 0
                              → pendingKeeperReward(1) == 0
carol 调 performUpkeep()       → keeperRewardOf(carol) == 0
```

### 修复

`withdrawFees` 为**当期**（仍 OPEN 的那一期）预留一份奖励额度：

```solidity
uint256 amount = accrued > reserved ? accrued - reserved : 0;
```

`reserved` 与发放额共用同一个 `_keeperRewardGross()`——这一点是刻意的：
两者一旦分叉，要么预留不足，要么界面报的数与实发的不一致。

三条边界都验证过：

- **预留不会堵死提费**：奖励恒为该期抽成的 20%，故只要有抽成，可提额就严格大于 0
  （`testFuzz_ReserveAlwaysCoversTheActualPayout` 在 1~1000 张票上断言这一点）；
- **零票的期不预留任何东西**（`test_EmptyRoundReservesNothing`）；
- **预留只是延后、不是沉淀**：该期开出后立刻可提。

新增 `withdrawableFees()` 视图，前端改为展示它——否则界面会对运营方虚报可提金额。

### 一个必须说清楚的连带影响

夹逼 ③ 现在在正常运行下**不再可达**（预留保证了 `accruedFees >= reward`）。
它**保留不动**，作为防下溢的最后一道防线。

因此 `LotteryKeeperReward.t.sol::test_RewardClampedToAvailableFees` 的断言被反转并改名为
`test_RewardSurvivesAFeeSweep`：**同一个场景照跑，断言从「拿 0」改为「足额拿到」**。
这不是为了让测试变绿而改断言——原测试把当时的实现行为当成了正确行为，
而那个行为正是本条发现。原文保留在测试的 NatSpec 里。

## A-2（Medium）— 弃期退款重新引入了 `claimTo` 修过的那个缺陷

### 机制

R20 M-1 发现：改用原生币后，没有 `receive`/`fallback` 的合约钱包中奖即等于弃奖
（`claim` 恒 revert `TransferFailed`），修复是加 `claimTo`。

FR-C-29 的退款通道是**在那之后**加的，而它只能付给 `msg.sender`。

**而且这一次更糟**：中奖至少还有 90 天后 `rolloverExpired` 把钱扫回缓冲区，
资金仍在流转；退款**没有任何过期兜底**——

- `rolloverExpired` 要求 `state == SETTLED`，作废期用不了；
- 作废期不可重复作废、不可 `retryDraw`；
- FR-C-24 禁止任何行政提款。

那笔票款于是**永久留在该期 `pot` 里**，成为偿付性恒等式里一笔永远无法清偿的负债。

### PoC

`test_ContractBuyerCanNeverBeRefundedFromAnAbandonedRound`（修复前）：
无 `receive` 的合约买 10 张 → 该期卡死作废 → `refundAbandoned` revert `TransferFailed`
→ 一年后 `rolloverExpired` revert `RoundNotSettled` → `pot` 分文未动。

### 修复

加 `refundAbandonedTo(roundId, rangeIndexes[], to)`，与 `claimTo` 同构：
Range 归属恒以 `msg.sender` 为准，`to` 只决定收款地址，**不增加任何权限面**
（有两条反向测试：非 Range 持有人调用 revert `NotRangeOwner`；`to == 0` revert `InvalidRecipient`）。

`TicketsRefunded` 事件仍记**购票者**而非收款地址，与 `PrizeClaimed` 同一口径。

## A-3（Medium）— CRE 桥接器把开奖奖励烧进一个取不出的余额

### 机制

SPEC Q8 的迁移路径是 CRE。CRE 的写入**只能**投递到实现 `IReceiver` 的合约，
所以链上落点是 `LotteryKeeperReceiver`，由它转调 `lottery.performUpkeep("")`。

于是 `performUpkeep` 里的 `msg.sender` 是**桥接器合约**，FR-C-30 的奖励
`s_keeperRewards[receiver] += reward` 记在它名下。而初版桥接器：

1. **没有任何代码路径**能调 `claimKeeperReward()`；
2. 即便有，它也**没有 `receive`/`fallback`**，`_sendValue` 必然 revert。

### 后果

每一期都有最多一张票价的运营抽成从 `s_accruedFees` 划走、进入一个**永远取不出**的余额。
`s_pendingKeeperRewards` 单调增长，成为偿付性台账上一笔永远无法清偿的负债——
合约余额永远回不到「全部债务已清」的状态。

这不是理论风险：`keeper-cre/luckyou-keeper/config.production.json` 里的
`receiverAddress: 0x8081f1cB…` 已经部署在 Base Sepolia 上，schedule 是每 5 分钟。
（本轮只读核对了链上状态：当前 `keeperRewardOf(0x8081…) == 0`，
因为实例是几分钟前刚重部的、第 1 期尚未开出——**这是时间问题，不是安全裕度**。）

### 为什么 21 轮都没看见

CI 的覆盖率闸是 `--no-match-coverage "script|mocks|cre"`。整个 `src/cre/` 被排除，
理由是「ReceiverTemplate 是 vendored 上游代码」（R20 I-4）。但那个目录里
**只有三个文件是 vendored 的**，`LotteryKeeperReceiver.sol` 是我们自己写的、
而且是生产 keeper 的链上落点。见 D-1。

### 修复

两条腿一起补：

- **桥接器**（改这一个就能救**已部署的** Lottery，不必重部 Lottery）：
  加 `receive()` 与**无权限、无自由裁量**的 `sweepKeeperReward()` ——
  金额与去向完全由链上状态决定，去向是构造时钉死的 `i_rewardBeneficiary`
  （刻意**不给 setter**：本合约的全部价值在于它没有可被滥用的杠杆）；
- **彩票侧**：加 `claimKeeperRewardTo(to)`，给所有合约 keeper 一条通用出路。

⚠️ **构造器签名变了**（多一个 `rewardBeneficiary`），桥接器必须重新部署并更新
`config.production.json` 的 `receiverAddress`。

## A-4（Low）— 锚点闸只装了一半

R20 L-4 加了 `anchorTime + 365 days >= block.timestamp`，挡住构造时追赶循环 OOG。
对称的另一侧无人看守，而**两侧都不可修复**（日程全合约无 setter，FR-C-24 禁止救援手段）：

| | 后果 | 性质 |
|---|---|---|
| 锚点过老 | 构造时追赶循环 OOG，部署直接失败 | 吵闹、无害 |
| **锚点在未来** | 第 1 期 `closeTime` 落在未来 ⇒ `performUpkeep` 永远不到期、期号永不推进。而 `buyTickets` 只看 state 与 closeTime，**实例照常收钱** | 安静、致命 |

PoC 里那个 `anchor = now + 3650 days` 的实例：`checkUpkeep` 恒 false、`performUpkeep`
恒 revert `DrawNotDue`，但 alice 能正常买到 10 张票。

`AuditR21Poc.t.sol` 里有一条测试**把这个当成合法配置**在断言
（`uint64(block.timestamp + 30 days)`，注释写「闸是单向的，只挡过老」）——
那个假设是错的，已改判并加反向断言。

修复：`if (anchorTime > block.timestamp) revert InvalidSchedule();`
锚点按定义就是「一个已经发生过的场次」，这道闸不会拒绝任何合法配置
（`Deploy.s.sol` 两个分支分别取上一个周二 12:00 UTC 与 `block.timestamp`，
后者恰好是边界，有专门测试钉住）。

## 2. 仍然未决 / 需要你拍板

1. **本轮四条合约修复都需要重新部署。** 最近一次提交是「冻结代码，开始多期验证」，
   而 `0x23bec642…` 是修复前的字节码。是否现在重部（会丢掉现有期次历史、
   需重加 VRF consumer、重部 CRE 桥接器并改 `config.production.json`）由你定。
   - **只有 A-3 可以不重部 Lottery 就缓解**：桥接器是独立合约，
     单独重部它即可让奖励流出来（新桥接器对旧 Lottery 完全兼容）。
   - 若暂不重部 Lottery，A-1 的现实影响是「keeper 奖励可能被提费清零」，
     A-2 的现实影响是「合约钱包买家在弃期拿不回钱」——两者都不影响普通 EOA 用户。
2. **R20 L-1（`buyTickets` 缺 `expectedRoundId`）仍未决。** 本轮复核仍成立：
   `injectPot` 收 roundId 而 `buyTickets` 不收，购票交易可能落进一个与用户预期不同的期。
   改签名 = SPEC 变更 + 前端改动 + 重部。
3. **R21 C-1（`injectPot` 不看暂停快照）仍未决**，需产品判断。
4. **R21 F-2（前端未暴露 `claimTo`）仍未修**。本轮判断优先级低：`claimTo` 的受益人是
   合约钱包，而合约钱包本来就不会用浏览器界面领奖。列在这里以免被当成已解决。
5. **前端只做了 `typecheck` + `next build`，没有在浏览器里实跑。**
   W-1 的退款卡片逻辑（扫 Range → 算金额 → 一键取回）**没有经过真实交互验证**，
   请勿当成「已确认可用」。
6. **本轮没能重跑 slither。** 本机 `slither` 在 PATH 上，但它要 spawn 一个独立的
