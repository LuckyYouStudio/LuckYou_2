# 多期验证方案

## 为什么需要它

到目前为止，**所有不变量只在 Foundry 里验过**。Foundry 跑的是 mock：VRF 立刻回调、
回调 gas 无限、时间由 `vm.warp` 说了算。而链上恰恰是这三件事最容易出问题：

- **VRF 回调有 gas 上限**，回调里做多了会静默失败，整期永远卡在 DRAWING
  （这条已经记在 `CLAUDE.md` 的踩坑清单里）
- **开期用的是「从锚点追到现在」的循环**，链上跑的是真实时间戳
- **跨期滚存释放（`CarryReleased`）从未在链上发生过一次** —— 这是全合约最复杂的一段逻辑

经历五次重新部署，**真实运行数据接近于零**。这不是代码问题，是验证缺口。

## 三个部件

### ① 观察器 `web/scripts/observe.mjs`

```bash
cd web && node scripts/observe.mjs
```

**它的全部价值在于独立性**：只读**事件**和**链上余额**，绝不调用合约的
`s_accruedFees` / `getRound` 之类的 getter 来做判定。拿合约自己的账本去验它自己的余额
是循环论证——账本算错时两边会一起错，对得严丝合缝。

核心检查是**资金守恒**。合约只有两个 payable 入口（`buyTickets` / `injectPot`）和
四条出账路径（领奖 / 提抽成 / 领开奖奖励 / 弃期退款），所以：

```
链上余额 == 购票额 + 注资额 - 已领奖 - 已提抽成 - 已领开奖奖励 - 已退款
```

任何一分钱的偏差都意味着存在未被事件记录的资金流动。**这条对不上就是严重问题，
不需要再讨论**。

其余检查：VRF 活性（每个 `DrawRequested` 都要等到 `DrawSettled`）、日程推进、
关键路径链上覆盖、FR-C-30 单期奖励不得超过一张票价。

回看历史实例（也是这个脚本的自检手段）：

```bash
LOTTERY=0x95b008Bc0B1969301a6d08828008aA66bC448627 START_BLOCK=45300000 node scripts/observe.mjs
```

> **只会打印 0 的检查器等于没有检查器。** 第一版就栽在这里：我手写的 `DrawSettled`
> 签名记错了（真实是 `(roundId, seed, ticketCount, perWinnerAmounts)`），topic0 对不上，
> 那个事件被静默漏掉，于是报告「第 1 期卡在 DRAWING」——可同一份数据里明明有人
> 领走了奖金，而 DRAWING 状态根本领不了奖。**是这个自相矛盾暴露了错误**。
> 现在事件签名一律从 ABI 取，这类错误从根上没了。

> **日程间隔不要求相等。** 开奖迟到时 `_advanceSlot` 会跳到下一个还来得及售票的场次，
> 所以间隔天然是「间隔的整数倍」。按等距去查会不停误报，而**误报比不查更糟**——
> 它会训练你忽略这一栏。真正有价值的是倍数本身：倍数 > 1 就是开奖迟到到跳过了场次，
> 这是 keeper 准时度的直接度量。

### ② 驱动器 `keeper/validation-driver.ps1`

没人推动就不会有期。每次运行做两件事：到点触发开奖；当前期票数不足就补买。

**为什么必须自动买票**：没人买票的期会以 `ticketCount == 0` 走 VOIDED。
那样跑一百期也只验证了 VOID 这一条路径，开奖 / 滚存 / 领奖 / 开奖激励全都碰不到。

**为什么不塞进 `keeper.ps1`**：keeper 是生产组件，只做「到点触发开奖」一件事。
让生产 keeper 含有「自动买彩票」的代码是错的，而且会无谓扩大它的权限面和资金面。

安全性质与 keeper 一致：**绝不回退到部署者 `PRIVATE_KEY`**（已实测：未配密钥时
写一行 ERROR 后退出，不做任何链上动作）；chainId 硬闸只允许 84532。
每期目标票数在 **3~6** 之间随期号循环。这个范围是**算出来的，不是随手取的**：

奖级名额是 `[1,2,5]`，`_settle` 里只有 `winners > ticketCount` 的奖级才不开出、
才会有钱进滚存缓冲区。也就是说**票数必须 < 5，三等奖才开不出**。
而且票价 `1e14` 因子太多——103 张票在 `[6000,2500,1500]` 三档下除得干干净净、
余数为 0，指望「取整余数」自然凑出 carry 是不成立的（第 1 期实测就是这样）。

用 `3 + (期号 % 4)` 让 3、4 各占四分之一，约每两期产生一次 carry；
下一期消费它时若超过自售额配比，还会顺带触发 `CarryWithheld`。
最初写的 `% 7` 要到第 7 期才出现第一次 3 张——**真坏了也得 14 小时后才知道**。

驱动器还会**领奖**（先 `cast call` 模拟、只在会成功时才发交易，避免每期盲发三笔
大概率 revert 的交易）和**领开奖激励**。不领的话通过标准第 6 条永远走不到，
而且观察器的资金守恒用的是「已领」而非「已计提」，那条路径会一直空白。

### ③ 调度

复用已有的计划任务基础设施（`keeper/install-task.ps1`）。
两条已经踩过的坑，脚本里都规避了：`.ps1` 必须存成 **UTF-8 with BOM**；
计划任务**不能直接 Execute `powershell.exe`**（会闪黑框并抢焦点），要经
`wscript.exe` 启动 `run-hidden.vbs`。

## 开跑前需要做的一步

驱动器需要一个**专用的低价值密钥**。它不需要任何特权——`performUpkeep` 和
`buyTickets` 都是无权限函数——所以**绝不能用部署者/owner 那把**。

```bash
~/.foundry/bin/cast wallet new ~/.foundry/keystores luckyou-driver
```

会提示设置密码，然后打印地址。接着：

1. 把密码写进一个文件（例如 `contracts/.keeper-pass`，已被 `.gitignore` 覆盖）
2. 在 `contracts/.env` 里加两行：
   ```
   KEEPER_ACCOUNT=luckyou-driver
   KEEPER_PASSWORD_FILE=C:\test\LuckYou_2\contracts\.keeper-pass
   ```
3. 用水龙头给这个地址打 0.05 ETH（Base Sepolia）

按每期 3~9 张、票价 0.0001 ETH 算，30 期票款约 0.02 ETH，加 gas 一周绰绰有余。

## 通过标准

跑到下面全部满足才算验证通过，缺一条都不算：

| # | 条件 | 为什么是它 |
|---|---|---|
| 1 | **≥30 期连续结算，0 期卡在 DRAWING** | VRF 回调 gas 在链上真的够用 |
| 2 | **`CarryReleased` ≥ 3 次** | 全合约最复杂的一段，至今链上零次 |
| 3 | **`CarryWithheld` ≥ 1 次** | 超配比扣留，与 2 是同一套规则的两面 |
| 4 | **`KeeperRewarded` ≥ 10 次，每次 ≤ 一张票价** | FR-C-30 的硬上限在真实数据下成立 |
| 5 | **观察器每次资金守恒 0 偏差** | 唯一一条不容讨论的红线 |
| 6 | **至少一次领奖 + 一次提抽成之后，5 仍成立** | 出账路径参与后账仍然平 |
| 7 | **期号连续，间隔均为整数倍** | 日程追赶逻辑在真实时间戳下正确 |

按 7200 秒间隔、keeper 准时算，一天约 12 期，30 期约 **2.5 天**；留出迟到与
排查余量，**按一周计**。

## 已知不在本轮验证范围内的

- **90 天领奖窗口过期滚存（`rolloverExpired`）**：等不起，只能靠单元测试
- **30 天弃期退款（FR-C-29）**：同上
- **`s_intervals` 无 getter**：观察器读不到日程，间隔基准靠 `INTERVAL_SECONDS`
  环境变量给。不值得为此改已冻结的合约，但记在这里
